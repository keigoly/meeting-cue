# 録音後の文字起こしし直し(修正 A)— Step 1 の計測(2026-10-16)

実会議で自分の発言の文字起こしが崩れ、振り返りに使えなかった(会議中の CER 36.6%・自分の行の 1 割に Whisper の幻覚の句)。同じ音声をまとめて書き起こすと読めるので、録音を止めた後にマイクと相手の録音をそれぞれ丸ごと認識し直す案(2026-09-27 に保留)を、まず Windows で測った。道具は `spikes/spike_redo.py`(認識)と `eval/redo_cer.py`(採点)。

## 素材

- 実会議 18.7 分(2026-10-16・Windows 版・ヘッドホン = 相手の声はマイクに回り込まない)。`audio/mic.m4a` と `audio/system.m4a`(16 kHz モノラル・録音の頭は同じ時刻)が別々に残っていた(書き出した `音声.m4a` は 2 本を重ねた 1 本)。
- 参照 = 重ねた 1 本を Air の whisper.cpp(`whisper-cli`・ggml-large-v3-turbo・`-l ja -mc 0`)でまとめて書き起こしたもの。**人が直した正解ではない**ので、CER は「参照との食い違い」の概算。
- 素材は会議の中身なので repo・Vault に入れない(`~/.meeting-cue/eval/` だけ)。

- 18.7 分の記録で、止めてから差し替えまで約 47 s の見込み(認識 42.2 s + 読み込み)。認識の時間は声の長さに比例する(VAD の後の声: 自分 732 s・相手 344 s)。

## 分かったこと

1. **時刻のずれが順序を壊す**。VAD で無音を除いてつないだ音声では、1 つの区間が除いた無音をまたぐことがあり、区間の時刻は前の声の側に付く(相手の発言が実際より 72 s 早く付いた例があった)。2 本を時刻で並べると話の順が崩れ、CER も下がらない(seq 34.4%)。語の時刻は元の時間軸に戻るので、**語と語の間で行を分けて行の時刻を語から取る**と 18.6% になる。分ける間の長さ(0.8〜3.0 s)では差が出ない。
2. **幻覚は消える**。VAD でつないで 30 s の窓で認識すると、自分の行の幻覚の句は 17 → 0(VAD なしでは無音から 1 行出た)。会議中は短い区間を 1 つずつ認識するので、文脈が無く幻覚が出やすい。
3. **細切れが解ける**。自分の行の平均 17.8 → 21.1 字(相手 18.9 字)。5 字以下の行は増えるが、中身は「はい」「そうですね」などの相づちで、重ねた 1 本の参照では落ちていたもの。
4. **10% 前後はこの参照では測れない**。同じ音声を同じ系統のモデルでまとめて書き起こしても、参照と 13.5〜16.6% 食い違う(参照の側にも固有名詞や同音の取り違えがある)。し直した文の残りの差(下限から +2〜5 点)は、2 本に分けたことで拾えた相づちと、重なった発話の並び順。
5. 語の時刻の揃い方で、まれに語の途中で行が分かれる(「ど|ちら」)。文字は失われない。

## 決定(Step 2 で入れる形)

- 方式は **seqw + 語の間 1.5 s**: `vad_filter=True`(既定の VAD)・`word_timestamps=True`・beam 5・temperature は既定(0.0〜1.0 の後退)・`condition_on_previous_text=False`。STT ヘルパーの `--redo <音声>` として入れ、契約(stdout の `ready` / `final` / `bye`・stdin の `quit`)は変えない。
- 1 本ずつ順に認識する(GPU は会議中のヘルパーが終わった後・+2.5 GB)。バッチ(batch8)は速さの差が小さく(約 15%)、字数が少なく出た(自分 2,519 字・seq は 2,942 字)ので使わない。

## Windows 実機の確認(Step 2 の後・2026-10-16 午後)

10-16 の記録の写し(`~/.meeting-cue/eval/redo-spike/copy/`)に `meetcue redo` をかけた。実際の記録とアプリには触れていない。

- **時間**: し直しは 42.3〜43.6 s(5 回)。自分 26.9〜27.1 s・相手 15.5〜16.5 s で、それぞれモデルの読み込み 2.1〜2.5 s を含む。起動直後の 1 回目だけ 50.3 s(自分 33.5 s・相手 16.8 s・読み込み 3.4 s と 2.2 s)。
- **CER は 18.5〜19.1%(暴走を縮めた後)**。ただし直す前は、6 回に 1 回 22.8% に落ちた:

| 出力 | CER | 自分: 行 / 平均字 / 幻覚 / 暴走 | 後退した区間(自分) |
|---|---|---|---|
| 直す前・暴走あり(`meetcue redo` 1 回目) | 22.8% | 137 / 22.9 / 0 / **4** | — |
| 直す前・暴走なし(ヘルパーを直に 3 回) | 18.6〜18.7% | 137〜144 / 19.7〜20.7 / 0 / 0 | 5〜15 |
| 直す前・暴走なし(`meetcue redo` 2 回) | 18.9 / 19.1% | 138・144 / 20.8・20.0 / 0 / 0 | 6・9 |
| **直した後(`meetcue redo` 3 回・1 回目は暴走を縮めた)** | **18.6 / 18.7 / 18.5%** | 137〜139 / 20.5〜20.6 / 0 / **0** | 1・7・5 |

6. **短い返事がまばらな窓は、し直すたびに文が変わる**。最後の 30 s の窓(1,053〜1,112 s・相づちと締めの挨拶だけの短い返事)は、毎回 temperature=0 の認識が目安(`compression_ratio` 2.4 / `avg_logprob` −1.0)に届かず、0.8〜1.0 の後退(乱数)で認識された。ほかの窓は temperature=0 で毎回同じ。後退した窓の文は、それらしい返事のこともあれば、「はい、」× 20 の行が 2 本(+389 字)出ることもある(6 回に 1 回)。
7. **暴走は縮めて抑える**: 同じ句(2〜15 字・文字を含む)が句読点をはさんで 4 回以上続くところを 1 回に縮める(`meetcue/redo.py` の `collapse_loops`・元の文は `raw`)。暴走した回は 4 行だけが縮み 22.8% → 18.6%。ほかの文 698 行(相手側・会議中・参照・Air の記録)では反応しない(数字の桁 `1,000,000,000,000` も縮めない)。後退した窓の文が毎回変わること自体は残る(乱数の種を決めても、どの文になるかは選べない)。
8. 見える化: metrics の `redo_transcribe` のチャネルごとの内訳に `fallback_segments`(後退した区間の数)と `loops`(縮めた行の数)を足した。`eval/redo_cer.py` は `loop_lines` を出す(決まった句だけの `hallucination_lines` では暴走を数えられなかった)。
9. **アプリの停止の流れ**(作業用のデータ置き場・ポート 8798・LOCAL・生成なし・同じ録音 2 本を 4 倍速で流し、録音の 16 分のところで停止を押した): 「録音中」は押して約 1 s で外れた(停止の処理 656 ms。今のアプリで録った 10-16 の実会議は 674 ms・10-09 は 934 ms)。「保存しています…」の間に「文字起こしを仕上げています… 5%〜99%」が進み、押してから 34.8 s で保存を終えた(し直し 33.7 s・15.8 分の録音)。記録は差し替えた文(158 行)になり、会議中の質問 15 件とサマリが残った。
