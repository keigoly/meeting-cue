# 会議の文字起こしに Soniox を使えるか — Step 1 の計測(2026-10-17)

REQUIREMENTS FR-2b(会議の認識に Soniox を選べるようにする)の前に、今の認識と Soniox を同じ音声で比べた。道具は `spikes/spike_soniox.py`(流す)と `spikes/spike_soniox_score.py`(採点)。素材・各方式の文字・結果は `~/.meeting-cue/eval/soniox-20261017/`(repo に入れない)。

## 素材と方式

| 素材 | 長さ | 正解(参照) |
|---|---|---|
| 自分の読み上げ(マイク) | 1.3 分 | 原稿(言い回しを変えて読んだ所も誤りに数える) |
| 首相の記者会見・冒頭発言(政府の公開動画) | 9.6 分 | 官邸が公開している会見録(人の書き起こし・フィラーは除いてある) |
| 首相の記者会見・質疑(司会・記者 7 人・首相が入れ替わる) | 23.8 分 | 同上 |
| 実会議(オンライン・自分と相手を重ねた 1 本) | 18.7 分 | Whisper large-v3-turbo の書き起こし(**機械の参照**) |
| AI の解説動画(一人語り) | 5 分 | YouTube の自動字幕(**機械の参照**) |

- **Mac(今)**: `meetcue run --source file:…`(SpeechAnalyzer + セグメンター・LOCAL・生成なし・実時間)。
- **Windows(今)**: 実会議だけ。会議中の文と、録音後のし直し(FR-9b・faster-whisper large-v3-turbo)。
- **Soniox**: `stt-rt-v5` を実時間で流す(endpoint detection・言語のヒント ja / en・**語彙なし**)。
- 採点: NFKC・記号と空白を除き、決めたフィラー(えー・あのー・まあ 等)を参照と方式の両方から除いてから、文字の編集距離 / 参照の字数。

## 結果

| 素材 | Mac(今) | Windows 会議中 | Windows 録音後 | Soniox |
|---|---|---|---|---|

| 記者会見・質疑 | 11.5% | — | — | **6.2%** |
| 自分の読み上げ | 36.7% | — | — | **24.9%** |

## 分かったこと

1. **人の書き起こしがある記者会見で、Soniox は誤りが少ない**。話し手が入れ替わる質疑では、Mac の約半分(11.5% → 6.2%)。
2. **読み上げの誤りは、言い回しの違いと固有名詞**。どちらの方式も、語彙を渡していない社名・製品名・地名を崩した。Soniox には語彙(`context.terms`)と置き換え辞書(FR-7)が要る。
3. **実会議は、機械の参照では差が出ない**。参照の中身を拾えた割合は Soniox 90%(Mac 77%・Windows 会議中 81%・Windows 録音後 91%)。Soniox は参照に無い字を参照の 34% ぶん足したが、足した塊の 3/4 は 5 字未満で、多いのは「はい」「その」「で」「そうですね」(参照の Whisper が落とした相づちと言い直し)。録音後のし直しが 18.6% と近く見えるのは、参照と同じ系統のモデルだから。精度を決めるには、人が直した参照(実会議の一部)が要る。
4. **確定の遅れ**: 話し続けると、Soniox の語が確定するまで中央値 5.5〜6.0 s(endpoint detection を使っても、切れ目は一人語り 5 分で 5 回・実会議 18.7 分で 125 回)。途中の文字はすぐ届く。finalize を送ると 0.2〜0.5 s で確定する(音声入力でも同じ)。→ 組み込むときは、途中の文字を partial として出し、セグメンターが間で finalize を送る(今の STT ヘルパーの契約どおり)。
5. **接続が切れることがある**: 13 本中 3 本(送信が 10 s 詰まった 2 本・相手から切られた 1 本)。原因は未特定(この時は Wi-Fi)。→ 長い会議では、切れたらつなぎ直し、その間の音はためて送る仕組みが要る。
6. Mac の stt-helper は、ファイル音源の 18.7 分の最後の finalize で止まった(会議中の経路は通らない・合成音声の試験では起きていない)。
7. 費用: この計測で流した音声は約 1.2 時間(Soniox の目安で $0.15 前後)。

## Windows の会議中と録音後・端末内の候補(2026-10-18)

記者会見 2 本(人の書き起こしあり)と実会議を Windows(RTX 4060 Ti 8 GB)で測った。素材・各方式の文・結果は `~/.meeting-cue/eval/win-local-20261018/`(repo に入れない)。

- **Windows 会議中**: 入れたアプリ(stable 516f716)の `meetcue run --source file:… --privacy local --no-llm`(セグメンター込み・実時間・作業用のデータ置き場)。
- **Windows 録音後**: `spikes/spike_redo.py` の seqw(FR-9b の録音後のし直しと同じ設定)で、モデル(large-v3-turbo = 今 / large-v3)と語彙(なし / 参加者と所属の 18 語)を変えた。語彙は会見録の司会の指名・記者の名乗りと、首相・与党の名前から取り、認識の誤りを見ずに決めた(`--hotwords`・faster-whisper の hotwords として毎回の窓の頭に渡す)。large-v3 は `Systran/faster-whisper-large-v3`(取った時点の commit を記録)。
- 測った間、壁紙のアプリが GPU を常に約 37%・1.8 GB 使っていた。

8. **会議中の文字起こしは、話し手が入れ替わると Soniox の誤りが約半分**。質疑で Mac 11.5%・Windows 11.3% に対して Soniox 6.2%。Windows の会議中は短い区間を 1 つずつ認識するため、実際の発言が「ご清聴ありがとうございました」「ご協力ありがとうございました」に置き換わった行が 23.8 分で 8 行あった(10-16 の実会議で見えたものと同じ。Soniox は 0 行)。一人語りの冒頭発言では差が小さい(7.4〜9.6%)。
9. **録音後のし直し(今の turbo)は、人の書き起こしに対して 4.6〜6.9%** で、Soniox の会議中より少ない。冒頭発言の 6.9% のうち 3.3 点は、会見録に無い司会の前置き(どの方式も書く)。残りの多くは表記の違い(頂く / いただく・僅か / わずか)と、会見録が整えた言い回し。誤りとして残るのは、同音の取り違え(首班 → 主犯・挑戦 → 朝鮮・薄氷 → 白票)・人名(小嶋 → 小島・照喜納 → テルキナ)・話し手が替わる所の短い挨拶の抜け。
10. **large-v3 は turbo とほぼ同じ**(6.5% / 4.6%)で、時間は約 3 倍・GPU は +1.9 GB。替えない。
11. **語彙を hotwords で渡すと悪くなる**(turbo 7.7% / 5.3%・large-v3 の質疑は窓の文が抜けて 9.0%)。語彙の 18 語を正しく書けた回数も、参照の 56 回中 turbo 46 → 45 回・large-v3 47 → 49 回とほぼ変わらない(直った語も壊れた語もある)。1.3 分の読み上げで効いたやり方は、長い録音では効かない。人名は置き換え辞書(FR-7)で直す。
12. 実会議は、参照が機械の書き起こし(turbo と同系統)で、2 本を時刻で並べるため行の長さでも点が動く(large-v3 は自分の行が長く 23.1%)。実会議で「ほぼ完璧」かを決めるには、人が直した参照が要る。

## アプリへの組み込み(2026-10-18・FR-2b の Step 2)

keigoly様 が「会議中に Soniox を選べるようにする」を選んだ。アプリと同じ経路(ヘルパーの `--pcm-out` → `meetcue/soniox_stt.py` → セグメンター → パイプライン)で、Mac の stt-helper(ファイル音源・実時間)に流して測った。作り方は REQUIREMENTS FR-2b の「組み込み」。

| 素材 | 方式 | CER | finalize → 確定 | 接続 | 備考 |
|---|---|---|---|---|---|

| 記者会見・質疑 | Soniox(10-17・流しっぱなし) | 6.2% | — | — | 上の表と同じ |
| 合成の面接(63 s・相手と自分の 2 本) | Soniox(アプリの経路・`meetcue app`) | — | p50 0.19 s / p90 0.72 s(10 回) | 0.5〜0.8 s | 判定と回答タブ・サマリまで |
| 記者会見・質疑(23.8 分)・**Windows 実機** | Soniox(アプリの経路) | **5.9%** | p50 0.18 s / p90 0.21 s(121 回・最大 1.29 s) | 0.54 s | 切断なし。送った音 1,426.5 s・約 $0.048 |

13. **セグメンターが区切って finalize を送っても、精度は変わらない**(6.2%)。発話ごとに確定させても(23.8 分で 119 回)、流しっぱなしの計測と同じ誤りだった。
14. **相手から切られることがある**: 23.8 分で 1 回、誤りの JSON なしで閉じられた(10-17 の「相手から切られた 1 本」と同じ型)。つなぎ直しで文は欠けなかった。閉じたときの WebSocket の番号と理由を `soniox_down` に残すようにした(次に起きたら原因を見る)。
15. **キーが違うと、接続は受け付けられ、設定を送った後に 401 が届く**(接続の時点では断られない)。1 s 以内に端末内の認識へ切り替わった。
16. 費用: 質疑 23.8 分で約 $0.048(1 本)。合成の面接 63 s × 2 本で約 $0.004。
17. 読み直し(2026-10-18・別の担当)で 4 件を直した: つないでもすぐ切られるのを繰り返すと切り替えに届かない(途切れの時計を接続をまたいで持つ)/ ヘルパーが bye の直後に終わると最後の確定を捨てる / 確定が遅れると同じ文が 2 回出る(セグメンターの safety_ms − 0.5 s で先に出す)/ 止めるときに Soniox の返事を待つ。
18. **Windows 実機でも同じ**(試験用の置き場とデータ置き場・入れてあるアプリは変えていない): ヘルパーの `--pcm-out` は 31 s の音声を 311 回に分けて欠けなく渡し、端末内の認識も続いた。質疑は 5.9%(Mac 6.2%。区切りの位置の違いの範囲)。違うキーは 401 の後に faster-whisper へ切り替わった。WASAPI のループバックからも `audio` が出る(何も鳴っていない間は音が来ない)。
19. **音も keepalive も届かないと、Soniox は約 21 s で 408 Request timeout を返して閉じる**(2026-10-18・音を送らない接続を 2 本並べて計測。keepalive を 15 s ごとに送った方は 75 s 保てた)。Windows のループバックは何も鳴っていない間は音を渡さないので、会議の始まりに無音が続くと切られる → 音を 8 s 送っていなければ keepalive を送るようにした。

## 次

- 会議で渡す語彙(`~/.meeting-cue/soniox_terms.txt`)を実会議で試す。費用を台帳(月の上限)に数える。
- Windows の録音後のし直しは今のまま(turbo・語彙なし)。Soniox で録った会議も、止めた後に Windows はし直す。
- 実会議の一部を人が直し、正しい参照にする(録音後の「ほぼ完璧」の確認と、会議中の方式の比較に使う)。
- 端末内のまま会議中を良くするなら、修正 B(会議中の final で決まり文句の幻覚を捨てる)。
