## 0. 要旨

会議・講演・オンライン会議の音声を **手元の Mac でリアルタイムに文字起こし**し、相手の発言が「自分への質問」だと **Jev(判定専用モデル)が数百 ms で判定**したら、**Obsidian Vault の知識**と**質問者の意図の読み**を添えて、**回答候補**と**こちらから返すべき逆質問の候補**を画面に即座に出す道具。自分が登壇者として質問を受ける側でも、参加者として登壇者に質問する側でも使う。

Meeting Cue! は録音して後で読む道具ではなく、「**聞きながらその場で出す**」道具。ローカル処理・mic/speaker の 2 チャネル・jq で扱える JSON・薄い UI を大事にする。

順番は **Mac → Windows → GitHub 公開**。公開リポジトリのコミット方針は別途相談(未着手)。

## 1. 背景と目的

| 項目 | 内容 |
|---|---|
| 困りごと | 会議中に質問されたとき、手元の資料や過去の知見(Vault に溜めたもの)を思い出して言葉にするまでに時間がかかる。講演を聴くとき、良い質問を組み立てる余裕がない。 |
| 目的 | 「質問の終わり → 最初のキュー表示」を **2.5 秒以内**にし、会話の流れを止めずに補助を受ける。 |
| 前提資産 | 作者の別プロジェクト(Zoom の同時翻訳)で **SpeechAnalyzer(macOS 26 内蔵・オンデバイス)の日本語ストリーミング STT・Core Audio process tap(相手側音声の取得)・最前面 NSPanel 字幕・ポーズ検出セグメンター**が実測済み(partial 追従 p50 59ms・1 時間連続で劣化 2.7%)。**コードは import せず、同じプロトコルの写しを本リポジトリに置く**。 |

## 2. 用語

| 用語 | 意味 |
|---|---|
| セッション | 1 回の会議・講演。開始〜終了で 1 ディレクトリの記録になる |
| チャネル | 音声の出所。`mic` = 自分(手元マイク)/ `system` = 相手(オンライン会議アプリの出力音声)/ `room` = 対面会議でマイクに入る全員 |
| 発話 | セグメンターが確定した 1 まとまりの文字列 |
| 判定 | Jev に発話を渡して得る型付きの答え(質問か・自分宛か・意図・分野・緊急度・回答長・知識要否) |
| キュー(cue) | 画面に出す補助カード。3 種: **回答候補** / **逆質問候補** / **ナレッジカード**(Vault の該当箇所) |
| モード | 自分の立場。`participant`(会議参加者)/ `presenter`(登壇者)/ `audience`(聴講者)。キューの重み付けと文面が変わる |
| 機微モード | クラウド送信を止める運用(`privacy = "local"`)。文字起こしと Vault 検索はローカルで動き続ける |

## 4. 機能要件

### FR-1 音声取得(2 チャネル)
- `mic`: 既定の音声入力(AirPods 等)を AVAudioEngine で常時取得。
- `system`: オンライン会議アプリの出力音声を **Core Audio process tap**(macOS 14.4+)で取得。対象はアプリ名の部分一致(`zoom` / `teams` / `chrome` 等)か PID。「システム全体タップ(自分のプロセス除外)」も選べる(Zoom の描画プロセスが版で変わる問題への対策・前例あり)。
- BlackHole 等の仮想デバイスは**使わない**(設定が増えるため)。
- チャネルごとに別プロセス(Swift ヘルパー)で動かし、片方が落ちても他方は続く。

### FR-2 リアルタイム文字起こし(オンデバイス)
- macOS 26 **SpeechAnalyzer / SpeechTranscriber**(`ja-JP` 主・`en-US` 可)。既定では音声をクラウドへ送らない(使う人が会議ごとに Soniox を選んだときだけ送る・FR-2b)。
- 部分認識(partial)を 400 ms 以内で追従し、確定(final)を出す。日本語は自動 final が出ないため、セグメンターの `finalize(through:)` で確定させる(前例の知見)。
- Swift ヘルパーの stdout は **1 行 1 JSON**(`ready` / `partial` / `final` / `bye`。`--pcm-out` を付けたときだけ認識に渡す音の `audio` も出す・FR-2b)。stdin は `finalize` / `quit`。Python 側はこのプロトコルだけを知る(Windows 版は同じプロトコルの別実装)。`start_s` はその文の**話し始め**(2026-09-27: 最初の語の時刻。結果の範囲は前の確定の終わりから始まり、間の無音を含むことがあるため。語の時刻が無ければ範囲の始まり)。Windows 版も話し始めを入れる。セグメンターが長さで切った final の切れ端を繰り越すときは、切り出した final の範囲と位置から始まりを見積もる(以前は最後の partial の範囲を使い、長い無音の後の質問が最大 60 s 早く記録されていた)。

### FR-2b クラウドの文字起こし Soniox を選べるようにする(2026-10-17 keigoly様・まず計測)
- 背景: 会議中の文字起こしが弱い。Mac は話し続けると確定が最大 59 s 遅れ(FR-3)、Windows は幻覚の句と自分の発言の細切れが出る(FR-9b)。同じ読み上げの録音で macOS 内蔵の認識は CER 44.9%、Soniox `stt-rt-v5` は語彙ありで 5.3%・話し終わりから確定まで 0.15〜0.42 s だった(2026-10-17 の読み上げの比較・自分 1 人の声)。会議の音(相手の声・システム音声)ではまだ測っていない。
- **送るかどうかは使う人が会議ごとに選ぶ**(keigoly様「使用者が任意で決められるようにする」)。既定は端末内。**LOCAL(FR-11)では選べない**(「クラウドへ何も送らない」の約束を守る)。選んだ会議は画面に Soniox を使っていると出す(送っていることを見て分かるようにする)。相手の声も Soniox(米国)に送られることを、選ぶ画面に書く。
- 方式: チャネル(mic / system / room)ごとに Soniox のリアルタイム WebSocket へ 16 kHz モノラルを流す。語彙(`context.terms`)は使う語だけを正しい表記で渡す(余計な語は取り違えの元になる。読み上げで PAN-OS を語彙の PaloAlto と書いた)。言語のヒントは日本語と英語(ヒントなしでは名前の羅列を韓国語と判定した)。鍵は `Authorization` ヘッダ(開始 JSON の `api_key` は 2027-01-15 から拒否)。話し言葉では語彙が効きにくい(RunPod をランポットと書いた)ので、置き換え辞書(FR-7)を必ず掛ける。
- 出力は STT ヘルパーの契約(FR-2 の `ready` / `partial` / `final` / `bye`・stdin の `finalize` / `quit`)に合わせ、パイプラインは変えない。Soniox に届かない(鍵なし・残高切れ 402・通信の失敗)ときは、そのチャネルを端末内の認識に戻し、画面と記録に理由を出す。
- **先に測る(Step 1・2026-10-17〜18 済み)**: 公開の動画(模擬面接・Jev の解説)・自分の読み上げ・Windows の実会議(18.7 分)で、今の認識(Mac の SpeechAnalyzer・Windows の faster-whisper)と Soniox を比べる(CER・確定までの秒数・幻覚の句・区切り)。結果は `spikes/SONIOX_STT.md`(話し手が入れ替わる記者会見の質疑で、会議中の誤りが Mac 11.5%・Windows 11.3% に対して Soniox 6.2%。Windows の会議中は決まり文句の幻覚の行が 8 行・Soniox は 0 行)。keigoly様 が 2026-10-18 に組み込みを選んだ。
- **組み込み(Step 2・2026-10-18・Mac と Windows で同じ本体)**:
  - 選び方: 「録音を開始」の「文字起こし」(このパソコン / Soniox(クラウド))。毎回このパソコンから始まる。LOCAL とキーが無いときは Soniox を選べない。Soniox を選ぶと、相手の声も Soniox(米国)へ送ることと 1 時間の費用の目安を出す。録音中と記録の題名の横に「Soniox」の印(端末内に切り替わったチャネルがあれば「Soniox(一部このパソコン)」・理由は印に)。キーは ⚙「会議の文字起こし(Soniox・任意)」(保存・確認 = `GET https://api.soniox.com/v1/models`・削除)。試験の入口は `meetcue run --stt soniox`。
  - 仕組み: 取り込み・録音・音量は今の STT ヘルパーのまま。`--pcm-out` を付けて起こすと、認識に渡すのと同じ音(モノラル s16le・標本の速さは ready の `dst_hz`)を約 0.1 s ごとに `{"type":"audio","seq":n,"pcm":<base64>}` で stdout にも出す(音声入力の dictation_helper と同じ形。付けなければ今までどおりで、既存の契約は変えない)。本体の `meetcue/soniox_stt.py`(`SonioxSTT`)がそれをチャネルごとに Soniox へ流し、語を契約の `partial`(まだ final にしていない確定した語 + まだ変わりうる語)と `final` に直す。パイプラインとセグメンターからは STTHelper と同じに見える。いつ確定させるかは今までどおりセグメンター: `finalize` → Soniox の finalize → `<fin>` までの語を 1 つの final(空でも返してセグメンターの待ちを終わらせる)。endpoint detection は使わない。語彙は `~/.meeting-cue/soniox_terms.txt`(`[soniox] terms_file`)があれば渡す(既定は無し)。置き換え辞書は今までどおりパイプラインが掛ける。
  - 届かないとき: 400 / 401 / 402 / 403 はすぐ、ほかはつなぎ直しが 45 s 続けて失敗したら、そのチャネルを端末内の認識に切り替える(会議の終わりまで戻さない)。ヘルパーは端末内の認識も続けている(画面には出さない)ので、Soniox で出せていなかった区間を端末内の final で補ってから先を流す。接続が切れたら(相手から切られた・送信の詰まり・処理の遅れが 15 s かつ応答も 15 s 無い。Soniox は無音でも約 1 s ごとに応答する・2026-10-18 実測)、出し終えた final の終わりから先の音(最大 90 s)を送り直してつなぎ直す。413(1 本 300 分の上限)もすぐつなぎ直す。切れている間に `finalize` が来たら、届いていた語をその場で final にする(セグメンターが待ちきれずに partial を出し、つなぎ直した後の文と重なるのを防ぐ)。途切れの時計と試した回数は接続をまたいで持ち、10 s 生きて処理が進んだ接続だけが戻す(つないでもすぐ切られるのを繰り返すと、つなぐたびに数え直して切り替えに届かなかった・2026-10-18 の読み直し)。finalize から `<fin>` が セグメンターの `safety_ms` − 0.5 s(相手側・自分 2.5 s)たっても来なければ、届いている語で final にし、後から確定した同じ区間の語は捨てる(遅れて届いた final が同じ文の 2 回目になるのを防ぐ)。止めるときは Soniox の終わりの返事を待たない(停止を遅くしない)。
  - 計測: metrics(rid = `STT`)の `soniox_connect`(ms・誤りの番号)/ `soniox_finalize`(finalize から `<fin>` までの ms)/ `soniox_down` / `soniox_stall` / `soniox_reconnect`(切れていた秒・送り直した秒・失った秒)/ `soniox_fallback`(理由・補った final の数)/ `soniox_done`(送った音の秒と費用の目安)。`meetcue report` に出す。記録の meta に `stt`(engine・model・region・語彙の数・切り替えたチャネルと理由)。費用は台帳(月の上限)にはまだ数えない。
  - 音を送らない間は 8 s ごとに `{"type":"keepalive"}` を送る(音も keepalive も無いと Soniox は約 21 s で 408 Request timeout を返して閉じる・keepalive を送った接続は 75 s 保てた・2026-10-18 実測)。Windows のループバックは何も鳴っていない間は音を渡さないので、会議の始まりの待ち時間に要る。
  - 実測(Windows 実機・2026-10-18・試験用の置き場とデータ置き場・入れてあるアプリは変えていない): ヘルパーの `--pcm-out` は 31 s の音声を 311 回に分けて欠けなく渡し、端末内の認識も続いた。合成の面接 63 s・2 本で finalize → 確定 p50 0.18 s・録音と止めた後の仕上げ(FR-9b)も動いた。記者会見の質疑(23.8 分)で **CER 5.9%**(finalize → 確定 p50 0.18 s / p90 0.21 s・切断なし)・その後の仕上げで 5.3%。違うキーは 401 の後に faster-whisper へ切り替わった。WASAPI のループバックからも `audio` が出る。
  - 実測(Mac・2026-10-18): 合成の面接 63 s・2 本で finalize → 確定 p50 0.19 s / p90 0.72 s・接続 0.5〜0.8 s。記者会見の質疑(23.8 分)をアプリの経路で流して **CER 6.2%**(流しっぱなしの計測と同じ)・finalize → 確定 p50 0.44 s / p90 0.50 s・途中で相手から 1 回切られ、1.82 s でつなぎ直した(失った音 0 s)。違うキーは接続の後に 401 が届き、1 s 以内に端末内へ切り替わった。Mac の tap-helper(相手の音)も実音で確認した(`--file` で afplay の再生だけをタップ・tap_create 0・準備 0.74 s・Soniox で 7 発話・finalize → 確定 0.18〜0.26 s・端末内の認識も裏で並行)。`--file` は afplay を先に鳴らしてからタップを作るので、頭の約 0.5 s は取れない(試験の入口だけの性質・会議の `tap-all` は先に取り込みを始めている)。

### FR-3 発話の確定(セグメンター)
- ポーズ検出(partial 更新が止まってからの経過 ms)と、末尾の形(文末・助詞・語中)で確定タイミングを変える。**音源で cadence が違う**: マイクは partial が数十 ms 間隔、会議アプリの出力(tap)とファイルは約 1 秒周期のバースト(実測ギャップ p50 976 ms / max 1,000 ms)。既定はマイク 500 / 900 / 300 ms、tap 1,200 / 1,600 / 1,100 ms(`[segmenter]` / `[segmenter_tap]`)。**自分の声(channel=mic)は tap と同じ長さ**(`[segmenter_self]`・2026-09-27 keigoly様 選択: 短く切ると文の途中で切れて文脈を失う。読み上げ 91 s を 6 回ずつ再現して CER 平均 28.6% → 26.4%・固有名詞以外 14.9% → 13.2%(揺れも 12.2〜16.3% → 12.6〜13.6% に縮む)。残る誤りは固有名詞(区切り方では直らない)。自分の発言は判定に使わないので確定の遅れは表示だけ)。対面の相手(room)はマイク用の短い値のまま。
- STT は節の途中にも句点を打つ(実測「…の文化。」「…シームと。」)ので、**句点だけで速く切らない**。「用言・丁寧形で終わり、かつ句点付き」のときだけ速い経路にする。
- 相づち(はい / ええ / うん / なるほど)は捨てる。
- 文末記号で分割し、未完結の切れ端は次の発話に繰り越す。
- **間が来ないまま話し続ける音声も切る**(2026-09-26 追加): 発話が `long_utterance_ms`(既定 8 s)を超えて partial に文末があれば、間を待たずに finalize する。`long_utterance_hard_ms`(既定 20 s)を超えたら文末がなくても切る。文末より後ろの言いかけは次の発話へ繰り越す。実測: 一人語り 5 分で 1 回の確定が抱える音声が p50 21.5 s / max 37 s → 9.2 s / 19.9 s(実再生の tap では max 59 s だった)。0 で無効。

### FR-4 判定層(Jev)
- 発話(`system` / `room` チャネルのもの)が確定するたび、Jev に **1 パスで固定の質問群**を投げる(§8)。目標 ≤ 500 ms(Air からの実測 272 ms)。
- 判定の使い道: (a) 質問かつ自分宛なら**キュー生成を起動**、(b) 質問でなくても分野が変わったら**ナレッジカードだけ**出す(LLM を呼ばない・安い)、(c) 緊急度と回答長で表示の優先度と文量を変える、(d) 意図をキュー生成のプロンプトに渡す。
- Jev に渡す state は「当該発話 + 直前 2 発話 + モード + チャネル」だけ(≤ 1,500 字)。会議全文や Vault 本文は渡さない。
- Jev が取れない(未設定・タイムアウト・非 200)ときは**ヒューリスティック判定**(疑問符・「〜ですか / でしょうか / 教えて / どう」等の末尾パターン)に落とし、判定なしでも動く。
- **全判定を記録**する(発話 id・答え・確率・所要 ms)。日本語での Jev の精度は公式に未検証(CJK)なので、記録から較正する(shadow mode の流儀)。

### FR-5 ナレッジ検索(Vault のローカル索引)
- Obsidian Vault を **SQLite FTS5(trigram トークナイザ)** で索引化。形態素解析器なしで日本語が引ける。目標 ≤ 50 ms / 検索。
- チャンクは見出し単位(上限 800 字)。ノートのパス・見出し・更新日を持つ。

### FR-9b 録音後の文字起こしし直し(2026-10-16 keigoly様・まず Windows)
- 録音を止めたら、マイクと相手の録音(`audio/<channel>.m4a`)をそれぞれ丸ごと認識し直し、記録の文字起こしを差し替える。話し手はトラックで決まる(mic = 自分 / system・room = 相手)。会議中は区間を 1 つずつ認識するため、自分の短い区間が文の途中で切れ、無音や短い区間から Whisper の幻覚の句(「ご視聴ありがとうございました」など)が出た(2026-10-16 実会議 18.7 分: CER 36.6%・自分の行の 1 割が幻覚入り)。まとめて認識し直すと 18.6%・幻覚 0(参照も機械の書き起こしなので下限は 13.5〜16.6%・`spikes/REDO_TRANSCRIBE.md`)。
- **会議中の文字起こし `transcript.jsonl` は消さない**(比べるため・戻すため)。し直した文は `transcript.redo.jsonl`(同じ形 + `source: "redo"`)に書き、`meta.json` の `transcript` を `"redo"` にする(`"live"` にすれば会議中の文に戻る・`meetcue redo <記録> --use live`)。質問の判定と回答候補は会議中の発言(`rid`)に付いたまま(回答タブの見出しは会議中の文)。し直した行には、時刻の重なる会議中の発言の判定を付けて、文字起こしの質問の印を残す。
- 置き換え辞書(FR-7)を差し替えた文にもかける(置き換える前の文は `raw`)。その前に、認識の暴走した繰り返し(同じ句が句読点をはさんで 4 回以上続く。「はい、」× 20 など)を 1 回に縮める(縮める前の文も `raw`。短い返事がまばらな窓は temperature の後退で認識され、6 回に 1 回出た・2026-10-16 Windows 実機)。サマリの要約と文字起こしの節は差し替えた文から作る(質問とキューの節は会議中の発言)。書き出しの文字起こしも差し替えた文。
- **停止の操作は遅くしない**: 停止で「録音中」はすぐ外れ、し直しは「保存しています…」の間に裏で行う(実測 18.7 分の記録で 42〜50 s・RTX 4060 Ti。声の長さに比例)。その間は次の録音を始められない(GPU を取り合わない・従来どおり記録は保存が終わってから一覧に出る)。失敗したとき・アプリを終えて取り消したときは会議中の文のまま(サマリは会議中の文から作る)。
- 方式(Windows): STT ヘルパーの `--redo <音声>`(faster-whisper large-v3-turbo・VAD で無音を除いてつなぐ・beam 5・前の文に寄せない・語ごとの時刻)。**語と語の間が 1.5 s 以上なら行を分け、行の時刻を語から取る**(VAD でつないだ区間は除いた無音をまたぎ、区間の時刻が前の声の側に付いて、2 本を時刻で並べると話の順が崩れた)。契約(FR-2 の `ready` / `final` / `bye`・stdin の `quit`)は変えない。1 本ずつ順に認識する(GPU +2.5 GB)。Mac のヘルパーは `--redo` を持たないので飛ばし、会議中の文のまま(Mac の方式は別途)。
- 計測: metrics の `phase=redo_transcribe`(`ms`・止めてからの `since_stop_ms`・`chars`・`lines`・`ok`・`error`・チャネルごとの音声と認識の長さ・temperature の後退で認識した区間の数 `fallback_segments`・縮めた行の数 `loops`)。`config.toml` の `[redo] enabled = false` で止められる(`gap_s` で行を分ける間)。
- 精度を上げる候補(2026-10-17 keigoly様「ローカルでもほぼ完璧に」・FR-2b の計測で一緒に測る): 端末内は large-v3(turbo でない)・語彙を渡す(読み上げでは whisper に原稿の固有名詞を渡して CER 4.6%)、クラウドは Soniox の録音後(ファイル)の認識(LOCAL では使わない)。「ほぼ完璧」を確かめるには、人が直した正解の文が要る(今の参照は機械の書き起こし)。

### FR-14 音声入力(2026-10-17 keigoly様・まず Mac)
- 会議の補助とは別に、**キーを押している間に話した言葉を、今使っているアプリに入れる**(Aqua Voice のような使い方)。Aqua Voice と同じ録音で比べた結果(2026-10-17・読み上げと普段の口述 35 本・`eval/aqua/`)、Soniox は日本語の精度が並び・英語は上・意味を書き換えない・費用は約 1/8 だったため、meeting-cue に組み込む(keigoly様 の方針)。
- 押し方(2026-10-18 keigoly様「Aqua Voice のように 2 回押しで」): **長く押して離す**(`hold_ms` 400 ms 以上)= 押している間だけ録る / **短く 2 回押す**(2 回目は 1 回目を離してから `double_ms` 450 ms 以内)= もう一度押すまで録る / 1 回だけ短く押したときは録らずに取り消す(貼らない・残さない・metrics `dict_cancel`)。押した瞬間から録り始めるので、長押しでも話し始めは欠けない。`[dictation] toggle_taps = 1` で初版(10-17)の「短く 1 回押すと、もう一度押すまで」に戻せる。
- 流れ: ホットキーを押す → マイクを開いて Soniox へ流す → 離す(2 回押したときは、もう一度押すまで録る)→ `finalize` → 確定した文に、フィラー除去(えー・あのー 等の決めた語だけ)と置き換え辞書(FR-7)を掛ける → クリップボードに入れて ⌘V で貼り付け、元のクリップボードを戻す。**AI による書き直しは入れない**(Aqua Voice は普段の口述 35 本中 6 本で意味を作り替えた。入れるかは使ってから決める)。
- 1 回ごとに録音(16 kHz モノラル)と文(認識のまま / 仕上げた文)と各段の時間を `~/.meeting-cue/dictation/` に残す(keigoly様「保存したものをローカルか自分の Google ドライブに」。Google ドライブは次の段)。
- LOCAL(FR-11)では Soniox に送らない(端末内の認識に切り替えるのは次の段。それまでは使えない理由を出す)。
- Mac の部品: ホットキー・マイク・貼り付けを 1 つの Swift ヘルパー(`helpers/macos/dictation_helper`)にまとめる。貼り付けにはアクセシビリティの許可が要る(許可が無いときはクリップボードに入れたことを知らせる)。Windows は Mac の後(同じ Python の本体・取り込みと貼り付けだけ差し替える)。
- 計測: 全段 `rid` 付きで `~/.meeting-cue/dictation/metrics.jsonl` に出す(キーを押してから音が届くまで・接続・音声の長さ・`finalize` から確定まで・仕上げ・貼り付け・離してから貼り終えるまで)。

#### FR-14b Aqua Voice の機能をそろえる(2026-10-19 keigoly様「キーバインドの設定を追加」「それ以外の機能も全て取り込む」)
Aqua Voice(v0.21.2)の設定と画面の項目を読み(アプリの中の日本語の表示と settings.json の項目名だけ・設定には書かない)、音声入力に関わるものを取り込む。設定は `~/.meeting-cue/dictation/settings.json`(アプリの「音声入力」の画面で変える・`meetcue dictate` も同じものを読む)。**既定は今の動きのまま**で、クラウドへ新しく何かを送る機能と AI の機能は、使う人が選んだときだけ動く。
- **キーバインド**(行ごとに鉛筆 = 押して決める・⋮ = 特別なキー / 既定に戻す / 外す・「デフォルトにリセット」):
  - 有効化(1〜3 個): 長く押す = 押している間・短く 2 回 = ハンズフリー(もう一度押すまで)。既定 ⌃⌥V。**1 つのキーだけでも使える**(Fn・右 ⌘ などの修飾キー・F1〜F20。10-19 keigoly様「Aqua Voice のように Fn だけを 2 回押して」。文字のキーだけは入力を奪うので使えない)。キーを決めるときは、ヘルパーが OS の見張り(CGEventTap)で次に押したキーを拾う(ブラウザは Fn を知らせないことがある・`{"cmd": "capture"}`)。**Fn・右 ⌘・右 ⌥ などの修飾キーだけのキー**も選べる(OS のキーの見張り = 入力監視の許可が要る。Fn は「🌐 キーを押して何もしない」にしてもらう)。修飾キーを押したまま別のキーを押したとき(⌥ + 文字など)は、録り始めた分を黙って捨てる。
  - ハンズフリーに切り替え: 有効化を押したまま押す(既定 Space = 「⌃⌥V+Space」。Aqua Voice の Fn+Space と同じ)。
  - ハンズフリーで始める(任意・既定なし): 押すと始まり、もう一度で終わる。
  - 最後の文字起こしを貼り付け: 既定 ⌃⌥⇧V(Aqua Voice の ⌘⌃V と重ならない)。
  - キャンセル: 既定 Esc・オン / オフ。録っている間だけキーを奪う(それ以外の Esc はふつうに効く)。取り消した分も文字にして履歴に残し(貼らない)、「最後の文字起こしを貼り付け」で戻せる。1 回だけ短く押したときの取り消し(FR-14)は今までどおり何も残さない。
  - 既定のキーは、併用中の Aqua Voice(Fn・Fn+Space・⌘⌃V)と重ならないものにする。登録できなかったキーは画面に理由(ほかのアプリが使用中・許可が無い)を出す。
- **有効化の方式**: 常にインスタント(既定・最後にまとめて貼る)/ ハンズフリー時のみリアルタイム / 常にリアルタイム(話して間(`[dictation] realtime_gap_ms` 500 ms・音の大きさで見る)を置くたびに `finalize` を送り、確定した分を貼る。Soniox は確定が話から約 5 s 遅れ、文末の「。」は次の音か `finalize` まで確定しない・endpoint の検出も 0.6 s の間では出ない(2026-10-19 実測)ため、確定を待つだけでは短い口述で何も貼れなかった。間で区切ると最後の「送信して」だけが短く残って聞き違えた(そう信して)ので、送信コマンドを使うときはその語を Soniox の語彙に足す)。AI で整える・編集モードのときはインスタントにする。
- **送信コマンド**: 文を区切って(「。」の後か口述の頭に)最後に「送信して」(送信・送って・send it)と言うと、その語を除いて貼り、送信キーを押す。読点の後や文の途中(「確認したら、送ってください。」「このメールを送信して。」)は本文のまま(途中までの文を送らない・10-19 読み直しの指摘)。送信キー: Enter(既定)/ ⌘+Enter / 貼り付けのみ(語だけ除く)/ オフ(語を残す)。**自動 Enter**: 選んだアプリでは、貼ったあと毎回 Enter を押す(既定なし)。
- **言語**: 日本語(英語まじり・既定 = 今のヒント ja,en)/ 日本語 / English / 自動。
- **辞書**: Soniox に渡す語(今の `terms.txt`)を画面で直す。**置換**: 音声入力だけの置き換え(`dictation/replacements.txt`・言い方 → 置き換え後。定型文やメールアドレス向け・`\n` で改行)と、会議と共通の置き換え辞書(FR-7)。
- **カスタム指示(AI で整える・既定オフ)**: 仕上げた文を、⚙ の生成 AI の接続先(速い役のモデル)に「認識の誤りと句読点だけを直す + 書いた指示」で直させる。失敗・8 s を過ぎたら直す前の文を貼る。直す前と後を履歴に残す。FR-14 の「AI による書き直しは既定で入れない」は変えない(オンにしたときだけ)。
- **編集モード(既定オフ)**: 文を選んだまま有効化を押して話すと、話した内容を指示として、選んだ文を AI が直して貼り替える(選んだ文はアクセシビリティで読む)。
- **画面の文脈(ディープコンテキスト・既定オフ)**: 押した時の前面のアプリ名・ウィンドウの題名・カーソルの前の文(最大 1,000 字)を Soniox の context に渡して精度を上げる(画面の文字が Soniox に送られる)。
- **カジュアルなメッセージ(既定オフ)**: Slack・Discord・LINE・メッセージなどでは文末の「。」(英語は文頭の大文字と文末の「.」)を付けない。
- **履歴**: 検索・コピー・録音の再生・削除・すべて消去(ゴミ箱へ)。前面だったアプリ・押し方・取り消しの印も出す。
- **ネットワーク**: Soniox までの接続の速さ(TLS の接続 ms で 最高 / 良好 / 普通 / 不良)・鍵の確認・最近の接続と確定の p50。
- **ステータス**: 待ち受けの状態・許可(マイク・アクセシビリティ・入力監視)・キーの登録の結果・使った量(今日 / 今月の回数・文字・音声の分・Soniox の費用の目安)・速さ(離してから貼り終えるまで p50 / p90)。
- **話している言葉の窓**(10-19 keigoly様「フローティングバーの上に字幕が出ていなかった」): バーの上に、話しているそばの文(確定した語 + まだ変わりうる語を、貼る時と同じ仕上げで)を出す。Aqua Voice の窓と同じ並び(左下 × = 取り消し・真ん中 = マイクの名前・右下 ■ = 止める)。止めた後は貼る文を出す。5 行を超えたら頭を「…」で削り、末尾を見せる。文は画面に出すだけで残さない。設定「話している言葉を出す」(既定オン・画面を共有しているときは相手からも見える)。
- **修飾キーだけのキーの待ち時間**: 右 ⌘ などで始めたときは、マイクはすぐ録り始め、音・バー・Soniox への接続は `[dictation] modifier_grace_ms`(300 ms)待つ。その間にほかのキーを押したら(⌘C などのショートカット)、何も出さずに捨てる(10-19 02:30 に右 ⌘ のショートカットで、録り始めの音とバーが一瞬出た)。
- **システム**: 音を鳴らす(既定オン・音の組 3 つ)/ フローティングバー(録っている間だけ = 既定・常に・出さない。画面の下に録音中の印・音の大きさ・経過秒・処理中・結果を出す。クリックでハンズフリーの開始と停止・右クリックで「最後の文字起こしを貼り付け」「取り消す」)/ 録っている間はほかの音を消す(既定オフ・出力の消音を戻し忘れないよう印のファイルを残す)/ クリップボード履歴に残さない(既定オン・nspasteboard.org の Transient / Concealed の印)/ マイクを選ぶ・マイクをテスト / 記録を残さない(プライバシーモード・既定オフ: 録音と文を保存しない・履歴に出ない)。ログイン時に起動はアプリのメニューバーの既存の項目を使う。
- **貼り先の確かめ**(10-19 読み直しの指摘): 離した時(リアルタイムで貼り始めたら押した時)と前面のアプリが違えば、貼らず・送信キーも押さない(文字にしている間に別のアプリへ移ったとき、文と Enter がそのアプリに入らないように)。バーに「アプリが変わったので貼りませんでした」と取り戻し方(最後の文字起こしを貼り付けのキー・無ければクリップボードへ)を出す。リアルタイムの途中で貼れなかったら(アプリが変わった・アクセシビリティの許可が無い)、その回はリアルタイムをやめ、貼れた分のあとを最後にまとめて貼る。クリップボードは貼り終えてから戻す(1.0 s・送信キーのときは 1.5 s)が、パスワードなど隠す印(Concealed / Transient)の付いた中身は戻さない(戻すとパスワード管理の自動消去が効かなくなる)。
- **LOCAL の録音中は使わない**: アプリで LOCAL(仕事の会議)を録っている間は、音声入力を断る(マイクの音・スピーカーから入る会議の声をSoniox に送らない)。
- **アプリでの待ち受け**: Meeting Cue! のアプリ(`meetcue app`)が起動している間、設定の「音声入力を使う」(既定オン)で待ち受ける。設定を変えたらすぐ効く(キーは登録し直す)。`meetcue dictate` と同時には動かさない(`dictation/listener.lock`)。キーを決める間は、すべてのキーの登録を外す。
- **取り込まないもの**(音声入力と別の機能・使っていない機能): 会議の翻訳(Live call translation)・コンピューター操作・Pins・アカウントとチーム・紹介・デモモード・画面の言語・マウスのボタンをキーにする機能。ペットは Aqua Voice のものではなく、ナギで作る(FR-14c)。履歴からの学習(Aqua Voice のサーバー側)は、置換と辞書を手で直す形で代える。
- 計測(FR-14 に足す): `dict_context`・`dict_lock`・`dict_cancel`(kind = tap / user / abort)・`dict_paste_last`・`dict_insert`(リアルタイムの 1 回分)・`dict_send`・`dict_ai`・`dict_edit`・`dict_bindings`(キーの登録の結果)。

#### FR-14c ナギのペット(2026-10-19 keigoly様「常時表示させて、動作も邪魔にならない、メモリとかも CPU とかも極力食わないように」・v0)
Aqua Voice のペットのように、ナギを画面の端に小さく出しておき、音声入力と会議の状態で表情と動きを変える。設計は Vault の `01_Projects/Meeting Cue/Nagi_Pet_Brief.md`。**v0 は今の 6 表情(`meetcue/ui/static/nagi/`)だけで作り**、絵を差し替えてもしくみは変えない(2D のコマ・Blender の 3D から書き出したコマは後の段)。
- **出し方**: 音声入力の設定「ナギ(ペット)」= 常に出す(既定)/ 録っている間だけ / 出さない、と大きさ(小・中・大)。既定の場所は画面の右下(Dock の上)で、胸から下の切れ目は窓の下に隠す(画面の下からのぞく形)。ドラッグで動かすと位置を覚える(`dictation/pet.json`・下の端の近くなら端にそろえる)。全スペース・全画面のアプリの上にも出る。音声入力の待ち受け(ヘルパー)が動いている間だけ出る。
- **邪魔にしない**: 前面のアプリから入力を奪わない窓(バーと同じ)。絵の透明な所のクリックは下のアプリへ通し、絵の上だけで受ける。カーソルが重なると薄くなる(30%)。右クリックで「隠す」「録っている間だけ出す」「大きさ」「位置を戻す」「音声入力の画面を開く」。左クリックは小さく跳ねるだけ(録音などは始めない)。
- **表情**: 待ち受け = idle / 音声入力で録っている間・会議の録音中 = listen / 文字にしている・会議の保存とサマリ = think / 会議で自分への質問を検知 = cue(1 回)/ 貼った・会議を保存した = done(1 回)/ 音声入力の誤り = alert(1 回)。音声入力の最中は会議の出来事で割り込まない。
- **軽さ**: ヘルパー(dictation-helper)の中で動かし、プロセスを増やさない。絵は表示する大きさに縮めて 1 回だけ読む。動きは Core Animation の層の変形だけ(絵を描き直さない)。コマ送りは OS の描画側(WindowServer)が行うので、ヘルパーの CPU はほぼ 0 のまま、描画側の負担がコマの数に比例して出る(10-19 の実測: うなずき続けると WindowServer の CPU が 1 コアの約 2.5% 増えた)。そのため続けて動くのは音声入力で録っている間(うなずく)と文字にしている間(揺れる)だけにし、待っている間は止まった絵で 12〜24 秒に 1 回、会議の録音中は 8〜16 秒に 1 回だけ小さく動く(回り続けるタイマーを持たない)。ゆっくりした動きは毎秒 20 コマ・速い 1 回の動き(跳ねる・指さす・困る)は 30 コマ。窓が見えない(ほかの窓に隠れた・画面が眠った・ロック)・視差効果を減らすでは動きを止める。低電力モードでは止めずに控えめにする(ゆっくりした動きは毎秒 15 コマ・時々の動きの間を 1.5 倍。10-19 の実測で、keigoly様 の Mac は電源につないだままでも低電力モードがオンだった)。
- **目標と計測**: 待っている間の CPU 平均 0.1% 未満・動いている間 0.5% 未満・ペットの分のメモリ +10 MB 以内(ペットを足す前のヘルパー: 7.1〜7.3 MB・CPU 0.005%)。ヘルパーが自分の CPU・実際のメモリ(phys_footprint)・起こされた回数を 1 分ごとに出し、`dictation/resource.jsonl`(phase `pet_resource`・ペットの状態つき)に残す。音声入力の「ステータス」と `meetcue report dictation` に出す。

### 5.3 プライバシーと境界
- 音声は既定でクラウドへ送らない(STT は既定でオンデバイス)。**例外は 2 つで、どちらも使う人が選んだときだけ**: 会議ごとに Soniox を選んだときのその会議の音声(相手の声を含む・FR-2b)と、音声入力で話した声(FR-14)。どちらも LOCAL(FR-11)では送らない。ほかにクラウドへ出るのは発話テキスト・直前文脈・Vault の該当チャンクだけ。
- 音声入力(FR-14b)で、選んだときだけクラウドへ出るもの: 画面の文脈(前面のアプリ名・ウィンドウの題名・カーソルの前の文 1,000 字まで → Soniox)/ AI で整える・編集モード(話した文・選んだ文・カスタム指示 → ⚙ の生成 AI の接続先)。どれも既定オフで、LOCAL では音声入力そのものを使わない(アプリで LOCAL の会議を録っている間も断る)。
- 本体の画面と API(127.0.0.1 だけで待つ)は、Host が 127.0.0.1 / localhost(そのポート)の要求だけを受け、POST は application/json だけにする(ほかのサイトのページや DNS の付け替えから、設定・履歴・鍵の API を使わせない・2026-10-19)。

### 5.4 可用性と縮退
- クラウド不通・鍵なし・台帳超過でも **文字起こし + ナレッジカード**は動く(段階的縮退)。落ちたときは画面に理由を出す。
- Swift ヘルパーが死んだら自動再起動(最大 3 回)し、記録に残す。
- 会議アプリの退出で自動停止(Zoom の CptHost 検知の前例)。初版は手動停止。

### 5.5 資源・熱
- M5 MacBook Air(24 GB・ファンレス)で 1 時間連続運転して遅延劣化 5% 以内(前例 2.7%)。
- 常駐メモリ: ローカル LLM を使わない構成で 1 GB 未満。機微モードでローカル LLM を載せると +2.3 GB(Qwen3-4B 4bit)。
- ナギのペット(FR-14c): 待っている間の CPU 平均 0.1% 未満・動いている間 0.5% 未満・メモリ +10 MB 以内(`pet_resource` で 1 分ごとに確かめる)。

### 5.6 可観測性(user CLAUDE.md Step 1)
- 全フェーズが `rid`(発話 id)・`phase`・`ms`・`ok`・`error` を JSONL に出す。`meetcue report <session>` で p50/p90 と失敗数を集計する。

## 6. システム構成

```
[自分の声]               [相手の声(Zoom/Teams/Meet)]           [会場の声(対面)]
   │ 既定の入力                │ process tap                           │ 既定の入力
   ▼                          ▼                                       ▼
┌─ Swift ヘルパー(macOS)───────────────────────────────────────────────────────┐
│  stt-helper (mic, ja-JP)        tap-helper (system, ja-JP/en-US)            │
│  SpeechAnalyzer → JSONL(partial/final) を stdout へ / stdin: finalize・quit │
└──────────────┬────────────────────────────┬──────────────────────────────────┘
               ▼                            ▼
┌─ Python オーケストレーター(meetcue)──────────────────────────────────────────┐
│  stt_reader → segmenter(ポーズ検出・相づち除去・文分割)                          │
│     ├─ judge: Jev(OpenRouter decisions) / heuristic(機微モード・失敗時)        │
│     ├─ knowledge: Vault FTS5 索引(~/.meeting-cue/index/vault.sqlite)         │
│     ├─ cues: LLM ストリーミング(OpenRouter Claude / ローカル MLX)              │
│     ├─ session: transcript / judgments / cues / metrics(JSONL)              │
│     └─ ui: terminal(Phase 1)→ FastAPI + WebSocket(Phase 3)                  │
└──────────────┬───────────────────────────────────────────────────────────────┘
               ▼
┌─ 表示 ───────────────────────────────────────────────────────────────────────┐
│  Phase 1: ターミナル  /  Phase 3: 最前面パネル(pywebview or NSPanel+WKWebView) │
│  ホットキー helper(Carbon)                                                   │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 処理フロー(1 発話)

1. `final` 到着 → セグメンターが発話を確定(`rid` 採番・`segment` を記録)。
2. `mic` チャネルは記録だけ(自分の発言は判定しない)。`system` / `room` は 3 へ。
3. Jev 判定(≤ 500 ms・並行して Vault 検索を先行実行)。
4. `question ∧ addressed_to_me` の確率が閾値以上 → キュー生成(ストリーミング)。閾値未満で分野が変わった → ナレッジカードのみ。
5. 表示更新・記録。生成中に次の質問が来たら古い生成を打ち切る。

| 層 | 選定 | 状態 | 理由 / 代替 |
|---|---|---|---|
| 本体言語 | Python 3.12(uv・`pyproject.toml`) | 確定 | 前例と同じ。Windows へそのまま持ち込める。代替: Swift 単体(Mac 専用になる) |

## 8. Jev の質問設計(固定・id は記録のキーになるので変えない)

state(例): `{"mode":"presenter","channel":"room","prev":["…","…"],"utterance":"その仕組みは既存の SIEM と競合しませんか"}`

| id | type | 問い(要旨) | 選択肢 / 段階 |
|---|---|---|---|
| `speech_act` | choice | この発話は何か | `question`(質問)/ `request`(依頼)/ `statement`(説明・主張)/ `agreement`(同意・相づち)/ `smalltalk`(雑談)/ `other` |
| `to_me` | noul | 私(モードの立場の人)に向けられた問いかけ・依頼か | — |
| `intent` | choice | 質問者が本当に知りたいこと | `clarify`(定義・確認)/ `how`(手順)/ `why`(理由・背景)/ `feasibility`(実現性)/ `cost`(費用・工数)/ `compare`(比較・代替)/ `risk`(懸念・リスク)/ `schedule`(時期)/ `opinion`(評価・意見)/ `challenge`(反論・指摘)/ `experience`(事例・経験)/ `other` |
| `needs_knowledge` | noul | 答えるのに私の資料・過去の経験(Vault)が要るか | — |
| `urgency` | score | 今すぐ返答が要る度合い | `low` / `medium` / `high` |
| `answer_length` | choice | 適切な返答の長さ | `short`(1〜2 文)/ `medium`(数文)/ `long`(構造化) |
| `topic` | choice | 分野(設定から生成・任意) | 例: `security_network` / `ai_agents` / `broadcast_tv` / `career` / `personal` / `other` |

- 起動条件(既定): `speech_act=question` の確率 ≥ 0.6 **かつ** `to_me` ≥ 0.6。`request` も同様に扱う。閾値は設定。
- 選ぶ係(FR-6b)の採点質問は `meetcue/judge/selector.py` の `ANSWER_QUESTIONS` / `COUNTER_QUESTIONS`(score 型・3 段階)。1 候補 1 呼び出し・並行。

## 13. 受け入れ基準(Mac 初版 = Phase 1〜3 完了)

1. 合成音声のテスト会議(60 秒・質問 3 件)で、3 件とも検出され、各キューが質問の終わりから **2.5 s 以内**に出る(`meetcue report` の p50)。
2. 実際のオンライン会議で **15 分以上**運転して落ちず、相手の質問に対し回答候補 3 件・逆質問候補 3 件・根拠ノートが表示される。
3. 機微モードで起動したとき、外向きの HTTP が 1 本も出ない(記録の `source` が全て `heuristic` / `local`)。
4. 全フェーズの所要 ms が JSONL に残り、失敗が画面と記録の両方に出る。
5. 秘密・個人パスがコードと既定設定に含まれない(公開前提)。
